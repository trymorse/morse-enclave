# Watch the door

`inference.trymorse.ai` is a door that ends TLS inside the enclave. Before a boot serves on a TLS key, it logs a record of that key in Rekor v2, Sigstore's public transparency log. The record is a `hashedrekord` entry whose certificate carries the boot's Nitro attestation document. The document attests the TLS key, the boot's HPKE key and the key's origin. A boot that cannot log its record never serves. `check-door.py` checks from outside that no certificate for the door's names holds a key without such a record.

The door's certificate also names `api.morseinference.com`, a second name for the door that is not open to the public yet. Each certificate it serves names `inference.trymorse.ai`, `api.morseinference.com` and a name derived from its key, so every certificate it serves appears in Certificate Transparency under `inference.trymorse.ai` too. The door also tells the relay which of its two names a request came in on. `check-door.py` watches `inference.trymorse.ai` when given no `--name`. Each `--name` replaces that default rather than adding to it, so to watch both names give both: `--name inference.trymorse.ai --name api.morseinference.com`. Morse's own watcher checks both names. It added `api.morseinference.com` once two things were true: a certificate the door ordered named it, because check 1 fails a name that no certificate in Certificate Transparency covers, and the CA had revoked the earlier wildcard certificates for `morseinference.com`, whose keys no record attests, so check 1 would fail on them.

Rekor v2 cannot be searched, so Morse lists the entries it logs in [trymorse/morse-records](https://github.com/trymorse/morse-records). `prod.jsonl` holds one pointer a line, `{"log": …, "index": …, "spki_sha256": …, "boot": …}`, and `leaves/<log>/<index>.json` holds a copy of each entry for the day a shard stops serving it. A pointer is only a hint. The watcher verifies the entry it names, prints a note for one that does not verify, and counts only those that do.

For each entry the watcher checks:

- the entry's inclusion in a checkpoint that the shard signed, with the shard's key from Sigstore's TUF repository, walked forward from the root the door's image embeds (`TUF_ROOT_SHA256`);
- that at least `WITNESS_K` operators of the witnesses in `WITNESSES` cosigned that checkpoint;
- the record in the entry's certificate. The watcher does not check the certificate's signature, which proves nothing. The record's Nitro document must verify under AWS's root at the document's own time, carry the PCRs of an image that `enclave_pins.json` in morse-pins listed unrevoked for prod at that time, attest the P-256 TLS key that the record and the entry's digest name, and carry a nonce that attests the record's origin.

`CHECKS` in the script lists what it then checks:

- Check 1: every certificate in Certificate Transparency for each name has a verified record within 20 minutes of being logged, and was issued before its key was 60 days old, unless its CA revoked it.
- Check 2: the histories of morse-pins and morse-records only grow.
- Check 3: the custody of each key ends at a key born in an enclave, with a floor that never falls.
- Check 4: each shard's tree only grows, by a consistency proof from the checkpoint the last run accepted.
- Check 5: CAA at each name names only Morse's ACME accounts.
- Check 6: every boot this watcher saw `/v1/attestation` list has a verified record of each TLS key it was listed holding, 2 hours after the watcher first saw it. For those 2 hours it cannot tell a boot that is still waiting on Rekor from one that never will log. What it catches is a boot that was listed and never got a record, both one still listed and one that died waiting for its record. That boot fails once its 2 hours end, and on every run after, because the watcher keeps every boot it has seen. The watcher reads the listing once a run, so a boot listed only between two runs cannot show. A live document from an image the pins do not list unrevoked fails at once. A boot that takes a handed key drops the key it was born with unlogged, so a born key it was listed holding before that take is a note, not a failure. Check 1 still fails any certificate for it. A boot that died before it could log a record has none, ever. Once you have read why, pass `--ack-boot <HPKE key id>=<URL of a public note>`, with the key id the failure names, and check 6 prints a note naming that boot and the note on every run instead of failing. Check 6 fails instead when the argument does not parse, and when that boot is live or has nothing left unrecorded. When this watcher keeps no boot with that key id, as after it loses its kept state, check 6 prints a note saying so. [UNRECORDED-BOOTS.md](UNRECORDED-BOOTS.md) lists the boots Morse's watcher acknowledges.
- Check 7: the public image signer's statements, and every push to morse-pins `main` and `sign.yml` run, pass the rules below.
- Check 8: no listed witness has missed a checkpoint of a shard still in service for 24 hours, no unknown one cosigns, and the newest pinned image's `internal/door/trust.go` here lists no witness `WITNESSES` does not, and no smaller k.
- Check 9: morse-records is public. GitHub's API, read with no token, must call it public. A 404 or a plain 403 fails. A 403 that names a rate limit, or a 429 that still refuses after the usual retries of GitHub reads, makes the run print a note and not judge check 9.

Check 1 asks a failing certificate's OCSP responder, then its CRL, and accepts an answer only when it verifies against the issuer that signed the certificate. It lists a revoked certificate as `revoked, skipped` and does not fail it. It still fails one whose revocation it cannot read, or that its CA holds and may release, and says why. A client that does not check revocation still accepts a revoked certificate, so a `revoked, skipped` line names a certificate that could have served the name.

Check 7 watches the public image signer, `.github/workflows/sign.yml` in morse-pins, whose statements decide which images a door hands its keys to. Every statement ever added to the `statements/images` branch must verify as the enclave verifies it: a Rekor v2 entry with `WITNESS_K` cosignatures, and a Fulcio certificate issued to `sign.yml` on `main` of morse-pins in the first attempt of a push or schedule run, at the commit the statement names. That commit must be on `main`, and the statement must say exactly what `enclave_pins.json`, the vendor pins files (the four at the root for a `morse-vendor-pins-v1` statement, or `v5/phala_pins.json` in place of the root's Phala file for a `morse-vendor-pins-v5` one), or an environment's `routes/<environment>/routes.json` and the `base` beside it, at that commit give, with its commit count as its sequence. GitHub's activity API must list every push to `main` since `sign.yml` was added, each starting where the last ended: data pushed by `morse-pins-publisher[bot]`, which never changes `.github/`, or a pull request an admin merged, which never changes a file the signer signs, a path under `routes/` or `v5/` included. Every commit's `.github/` tree must be one `SIGNER_TREES` names, and no `sign.yml` run number may be missing, since a deleted run leaves a gap.

- A new `.github/` tree fails check 7. Read the change to the signer's code, then pass `--signer-tree <tree>` to allow it.
- Morse lists a change's tree in `SIGNER_TREES` before the change merges in morse-pins, so its own watcher never sees `main` off the list. A tree names its exact content, so listing it trusts only the change that was read. A morse-pins pull request that changes `.github/` prints, in its `signer-allowlist` check, the tree `main` will hold once it merges, and that check fails until `SIGNER_TREES` on the `main` of Morse's backend names that tree. The order is therefore: open the morse-pins pull request, merge the backend change that lists the tree its check printed, run the check again, then merge the morse-pins pull request. When another change to `.github/` merges in morse-pins first, the tree changes, and the new one must be listed the same way.
- A refused push, a push that does not start where the last ended, a refused `sign.yml` run, or a missing run number fails every run. Once you have read a refused push, pass `--ack-refused <sha>` once, with the commit the push ends at, which the failure names. For a refused or missing run, pass `--ack-run <number>` once, with the run number the failure names. Each clears that push or run and no other.
- A run that has not completed stays pending. Check 7 judges it when it completes, or fails it as missing when it is deleted.
- A push the activity API has not yet listed is a note until this watcher has seen `main` unlisted for an hour, and then it fails.

On its first run a new watcher checks only the last 14 days: the pushes to `main` since the one 14 days back, while its state holds no `last_push`, and the `sign.yml` runs created since then, while it holds no time of its last runs read, so the runs before them do not count as missing. When that first run cannot read the activity, or lists no run in the window, the next run starts that part afresh. Later runs carry on where it stopped. The state keeps the id and time of the last push event on `main` that check 7 judged, as `last_push`. Each run reads the activity newest first back to that event, then judges the newer pushes oldest first, even when `main` is back where it was. If the activity no longer lists that event, check 7 fails and keeps its state. Check 7 keeps no tip of its own: `tips["morse-pins"]` is check 2's. It reads GitHub's API with no token, at most two requests a run once it has caught up, and uses `GH_TOKEN` when it is set. It is not enforced on a run that cannot reach the API.

The witness list is the script's own on purpose, so one change to this repository cannot relax both the enclave and the watcher. When check 8 fails on a new witness, read the change before you add it.

It needs [uv](https://docs.astral.sh/uv/) and full clones of the three repositories:

```sh
git clone https://github.com/trymorse/morse-pins
git clone https://github.com/trymorse/morse-records
git clone https://github.com/trymorse/morse-enclave
uv run check-door.py --pins morse-pins --records morse-records --enclave morse-enclave \
  --caa-history caa.jsonl --sequence-state state.json \
  --caa-account letsencrypt.org=<account URI> --caa-account pki.goog=<account URI>
```

Take the two account URIs from the CAA record of `inference.trymorse.ai` the first time. Each run adds one CAA sample to `caa.jsonl` for each name whose CAA lookup succeeded, and none for a name whose lookup failed, and fails if a sample names any other account, or if a name has no sample. A sample from before the watcher took several names names no host and counts as `inference.trymorse.ai`'s. Pull the three clones and run the script at least every 5 minutes, and keep `state.json`, `caa.jsonl` and the `state.json.cache` directory between runs. The state holds each shard's last accepted checkpoint, the commits each repository's `main` was at, and every boot seen live. For check 7 it also holds where it stopped in the activity of morse-pins `main`, the highest `sign.yml` run number judged and when the runs were last read, the runs still pending, the refused or missing runs and refused pushes not yet acknowledged, the statements already verified, and since when `main` has been unlisted. A clone or a pull of morse-pins fetches `statements/images` as `origin/statements/images`, which check 7 reads. The watcher enforces check 6 only on a run within 7 minutes of the last. It reads CT from crt.sh and certspotter for each name. When one of them cannot be read for a name, check 1 prints a note naming it and the error and judges that name from the other. When neither can be read for one name, or one answers with an entry for it the script cannot parse, check 1 is not enforced for that name on that run and still judges the others. When neither can be read for any name, the run cannot read its evidence. The CAA record is read the same way: one that cannot be read for a name leaves check 5 not enforced for that name on that run, and the samples of the other names are kept. crt.sh sometimes answers with no certificate for the name while certspotter returns some, so when certspotter returns some or cannot be read, the script reads crt.sh twice more, 2 and 5 seconds apart, and if it still has none, takes it as unread. The script exits 0 when every check passes, 1 when one fails, and 2 when none fails but a check is not enforced. With `--verdict verdict.json` it also writes that outcome as JSON: the kind of run (`passed`, `failed`, `unenforced`, or `unread` when it could not read its evidence), the exit code, whether a retry may read the evidence, the checks that failed and those not enforced, each check's messages, each CT source with why it could not be read, or null when it was read, the names each CT source was read and not read for, each certificate judged with its fingerprints, validity, names and check 1's judgment of it, and the names whose evidence failed check 1 or check 5, or when no check failed, the names those two checks left not enforced. The alert's title names them.

To run it on a schedule, `door_watch.py` wraps the command. It tries a run that could not read its evidence twice more, 20 seconds apart, keeps how many runs in a row ended the same way in `<state dir>/streak`, and with `--alerts` names the alert a run sends: a failed check at once, a run with no kept state at once, and the third run in a row that could not read its evidence or left a check unenforced. It also keeps, in `<state dir>/ct-streak`, how many runs in a row each CT source could not be read or parsed for at least one of the door's names, and alerts, under its own label, on a run that finds 36 or more such runs in a row and no alert sent for them. When the source read some names on some of those runs, the alert says the source's coverage was incomplete rather than wholly unavailable and names each name it missed at least once. When it missed every name, the alert names, from the last of those runs, the names each other source read and those none did. A source listed as reading a name parsed what it returned for it, and one that answered with an entry that does not parse counts as not reading that name. Neither says which names check 1 enforced, since a name another source read is still not enforced when a third answered for it with an entry that does not parse: check 1's NOT ENFORCED lines in the run's output say so. The workflow marks the source `alerted` in `ct-streak` once the alert is sent, so a send that fails is tried again on the next run and each outage alerts once. A run that reads the source for every name restarts its count, and a run that could not read its evidence leaves the count as it was. Morse's `door-watch` workflow runs it as `python3 door_watch.py --state door-state --alerts --restored <cache key> --run-url <url> --alert-body alert.md --ct-alert-body ct-alert.md -- uv run check-door.py ...`.
